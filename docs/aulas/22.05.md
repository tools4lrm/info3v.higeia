# Projetando e Implementando o REQ.003, REQ.004 e REQ.005 do Projeto

## Transição entre Engenharia de Requisitos e Desenvolvimento

Prezados alunos, até o presente momento no projeto hospitalar (Sistema Higeia), estive concentrados na fase de **Planejamento** e **Engenharia de Requisitos**. 
Compreendemos as dores dos usuários, mapeamos as regras, **escrevemos as Histórias de Usuário** (_User Stories_) e definimos seus respectivos **Critérios de Aceitação**.

Agora, estou cruzando a linha que divide o escopo puramente **funcional** da sua **implementação prática**. Estamos entrando oficialmente na fase de **Desenvolvimento**.

> **ATENÇÃO**: O Maven e o Git devem estar configurários do VS Code, como nas aulas anteriores.

## 1. O Fluxo de Processo: Fases, Atividades, Papéis e Artefatos

Para realizar essa transição sem perder a rastreabilidade do software, precisamos entender a engrenagem que move um processo de desenvolvimento de software. 
Baseando-se no ciclo padrão da engenharia de software, dividimos a evolução do nosso projeto através de quatro pilares:

 - **Fases**: Os grandes blocos macro temporais do projeto (onde estamos vs. para onde vamos).
 - **Atividades**: As ações práticas realizadas dentro de cada fase (o "fazer" do dia a dia).
 - **Papéis**: Quem executa a ação. Em ambientes de aprendizado e times ágeis, você alterna de papéis constantemente (ora atuando como analista, ora como arquiteto, ora como desenvolvedor).
 - **Artefatos**: Os subprodutos palpáveis gerados por uma atividade que servem de entrada/base para a próxima etapa (documentos, diagramas, códigos, arquivos de banco de dados).

## 2. Compreendendo o Ecossistema do Projeto: Modelo, Serviço e Repositório

Como estamos construindo nossa aplicação de forma nativa com Java Puro e Maven (sem delegar o controle para a "mágica" das configurações automáticas do Spring Boot), 
a arquitetura do projeto e a separação de responsabilidades tornam-se nossa obrigação.  

Lembrem-se, estamos desenvolvendo algo complexo, tudo que envolve muitos elementos pode e deve ser considerado e tratado com complexo. 
Um princípio básico para lidar com a complexidade é quebrar em partes menores com intuito de tornar o projeto seja sustentável, modular e fácil de testar. 
Para isso, tomei a decisão de, neste momento, dividir em um ecossistema com três componentes fundamentais:

### A. Modelo (`br.edu.ifrn.higeia.modelo`)

Representa o estado e a estrutura de dados do mundo real. São classes conhecidas como POJOs (Plain Old Java Objects). Elas contêm apenas os 
atributos privativos da entidade e métodos que sabem responder sobre seu estado intrínseco (interno).  

Exemplo: A classe `Ala.java` guarda o nome, capacidade e leitos ocupados. Ela possui lógica interna como `isLotada()`, mas ela não sabe se 
existe outra ala duplicada no sistema ou como salvar a si mesma no banco de dados.

### B. Serviço (`br.edu.ifrn.higeia.servico`)

É o "cérebro" das regras de negócio do sistema. Esta camada é responsável por ditar o comportamento do software e fazer cumprir os **Critérios de Aceitação**.  

Exemplo: A classe `AlaServico.java` recebe uma instancia da classe `Ala.java`. Ela verifica se a capacidade é menor ou igual a zero e lança uma exceção caso positivo, 
impedindo que dados corrompidos avancem no sistema.

### C. Repositório (`br.edu.ifrn.higeia.repositorio`)

**AINDA NÃO IMPLEMENTADO**, mas é a camada responsável exclusivamente pela persistência e comunicação **externa** com o mecanismo de armazenamento.  

Exemplo: **AINDA NÃO IMPLEMENTADO**, mas será representada pela classe `AlaRepositorio.java` que conterá os comandos SQL (INSERT INTO, SELECT * FROM). 
Ela não questiona se os leitos são maiores que zero ou se o nome é bonito; ela apenas executa o comando solicitado pelo serviço e salva o estado do modelo no disco de forma permanente.

## 3. Atividade Prática: Abstração e Modelagem dos Requisitos Restantes

Para consolidar a transição da fase de planejamento e requisitos para o desenvolvimento prático, vocês atuarão como **Projetistas** / **Arquitetos de Software** nas próximas três histórias de usuário cruciais do Projeto.

### O que você deve fazer (Passo a Passo da Atividade):

Aplique a Técnica dos Substantivos: Leia os requisitos que foram especificados e identifique os novos objetos candidatos a se tornarem classes de Modelo (ex: **no meu caso**, criar a classe `Leito.java`).

1. Determine as Ações do Serviço: Identifique quais validações e métodos deverão nascer na camada Service para garantir que as regras e exceções dos critérios de aceitação funcionem.
2. Escreva o Esboço no Código: No seu VS Code, crie as novas classes de modelo ou adicione os métodos necessários nas classes existentes.
3. Sincronize com o GitHub: Assim que terminar de estruturar suas assinaturas e classes, execute o ciclo de sanidade estudado
   - `git add`
   - `git commit -m "Modelagem e esqueleto das classes REQ.003, REQ.004 e REQ.005"`
   - `git push`
