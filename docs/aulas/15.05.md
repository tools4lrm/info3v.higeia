# Projetando e Implementando o REQ.001 e REQ.002 do Projeto

Agora que seu ambiente está configurado e o projeto Maven inicializado, vamos dar o primeiro passo no desenvolvimento: A **Análise**. Programar não é apenas digitar 
código, o código é uma consequência de um modelagem/projeto de problemas do mundo real para uma linguagem que o computador entenda. Essa tradução é guiada por um conjunto de atividades executadas por pessoas com intuito 
de gerar artefatos de software (**Processo de Software**).

> **ATENÇÃO**: O Maven e o Git devem estar configurários do VS Code, como nas aulas anteriores.  

## 1. O que é Análise de Requisitos? 

A **análise de requisitos** é uma atividade do processo de software que tem a responsabilidade de compreender **o que** o sistema deve fazer. No modelo **Ágil de Desenvolvimento**, 
usamos Histórias de Usuário (User Stories) para descrever funcionalidades sob a perspectiva de quem vai usar o sistema. Nosso trabalho é ler essas histórias e identificar os 
elementos que se tornarão código.

> **ATENÇÃO**: Para mitigar os desperdício dentro do **Processo de Desenvolvimento de Software**, só modelamos, projetamos e implementamos aquilo que está requisitado por algum
> interessado do sistema. 

## 2. Da História para o Objeto: A Técnica dos Substantivos

Uma forma clássica e eficiente de começar a modelagem Orientada a Objetos é analisar o texto dos requisitos buscando por substantivos e verbos:

 - **Substantivos (Objetos/Entidades)**: Geralmente representam as classes e seus atributos. Ex: "Ala", "Leito" ...
 - **Verbos (Ações/Métodos)**: Geralmente representam os comportamentos ou funcionalidades. Ex: "Cadastrar", "Validar", "Listar" ...

## 3. Análise das Nossas Histórias ([REQ.001](https://github.com/tools4lrm/info3v.higeia/blob/55f4d12ae19fab589aa0162f1c4961d3c1d6e81e/docs/requisitos/RF.001.md) e [REQ.002](docs/requisitos/RF.002.md))

Ao analisarmos os requisitos de **Cadastro** e **Visualização de Alas**, identificamos os seguintes candidatos:

### Entidade: Ala 
- Atributos (O que ela tem):
  - nome ou codigo (String)
  - capacidadeMax (int)
  - leitosOcupados (int) - Necessário para a regra de negócio da REQ.002
- Regras de Negócio (O que ela deve validar):
  - Capacidade deve ser maior que zero.
  - Saber se está lotada (leitos ocupados == capacidade total).

## 4. Organização de Pacotes no Maven

No Java, organizamos as classes em "pastas" chamadas pacotes (packages). Isso mantém o projeto limpo e profissional. Seguindo o padrão de mercado, 
usaremos a seguinte estrutura dentro de `src/main/java`:

 - `br.edu.ifrn.higeia.modelo`: Onde ficam as entidades (as "coisas" do sistema).
 - `br.edu.ifrn.higeia.repositorio`: Onde ficaria a lógica de salvar os dados (arquivos ou banco).
 - `br.edu.ifrn.higeia.servico`: Onde ficam as regras de negócio (validar duplicidade, validar número de leitos).

## 5. Representação das Classes 

Veja como a história do usuário se transforma em uma estrutura de classe Java:

### A Classe de Entidade (modelo)

Esta classe representa a Ala em si.

``` java

package br.edu.ifrn.higeia.modelo;

public class Ala {
    private String nome;
    private int capacidadeMax;
    private int leitosOcupados;

    // Métodos para calcular disponibilidade (REQ.002)
    public int getLeitosDisponiveis() {
        return this.capacidadeMax - this.leitosOcupados;
    }

    public boolean isLotada() {
        return this.leitosOcupados >= this.capacidadeMax;
    }
    
    // Getters e Setters...
}

```

### A Classe de Regra de Negócio (service)

Aqui é onde aplicamos os Critérios de Aceitação (impedir nomes duplicados e validar número de leitos).

``` java

package br.edu.ifrn.higeia.service;

import br.edu.ifrn.higeia.modelo.Ala;

public class AlaServico {
    public void cadastrarAla(Ala novaAla) {
        // Critério de Aceitação: Validar leitos > 0
        if (novaAla.getCapacidadeMax() <= 0) {
            throw new IllegalArgumentException("A capacidade deve ser maior que zero.");
        }
        
        // Lógica para verificar duplicidade e salvar...
        System.out.println("Ala " + novaAla.getNome() + " cadastrada com sucesso!");
    }
}

```
## 6. Experimentando o Código na Prática (Testando)

No Maven, sua classe principal geralmente fica em `src/main/java/br/edu/ifrn/Main.java`. Irei utilizá-la para criar instâncias da classe Ala e testar os critérios de aceitação. 
Veja como podemos testar os requisitos REQ.001 e REQ.002 manualmente:


``` java
package br.edu.ifrn;

import br.edu.ifrn.higeia.modelo.Ala;
import br.edu.ifrn.higeia.servico.AlaService;

public class Main {
    public static void main(String[] args) {
        // 1. Instanciando o serviço e o objeto
        AlaService service = new AlaService();
        
        Ala alaUti = new Ala();
        alaUti.setNome("UTI Cardiovascular");
        alaUti.setCapacidadeMax(10);
        alaUti.setLeitosOcupados(8);

        // 2. Testando a Regra de Negócio (REQ.001)
        System.out.println("--- Teste de Cadastro ---");
        try {
            service.cadastrarAla(alaUti);
        } catch (Exception e) {
            System.err.println("Erro ao cadastrar: " + e.getMessage());
        }

        // 3. Testando a Visualização e Cálculos (REQ.002)
        System.out.println("\n--- Status da Ala ---");
        System.out.println("Ala: " + alaUti.getNome());
        System.out.println("Capacidade Total: " + alaUti.getCapacidadeMax());
        System.out.println("Leitos Disponíveis: " + alaUti.getLeitosDisponiveis());
        
        if (alaUti.isLotada()) {
            System.out.println("Atenção: Esta ala está LOTADA!");
        } else {
            System.out.println("Status: Há leitos disponíveis.");
        }
    }
}

```
    
## 7. Fluxo de Trabalho: O Ciclo de Sanidade do Desenvolvedor

Trabalhar no **desenvolvimento de software** exige organização por ser uma atividade **complexa** e **colaborativa**. Se dois desenvolvedores mexem no mesmo arquivo sem ordem, o caos se instala. Por isso, seguimos este **ciclo lógico e obrigatório**:

### 7.1. Sincronizar (git pull)

Antes de digitar uma única linha de código, você deve trazer as atualizações do servidor para sua máquina local.
> O comando `git pull`, antes de iniciar qualquer mudança no seu repositório local, garante que você está trabalhando na versão mais recente do projeto e evitar conflitos com o trabalho de seus colegas que já foi enviado ao GitHub.
